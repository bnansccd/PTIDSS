# 第一部分 多角色需求理解与评审结论

> 本部分以五个专业角色视角对 PRD V1.1 进行深度解读，输出各角色的理解要点、关注重点、评审意见与开发基线建议。

## 一、产品经理视角：需求解读与产品规划

### 1.1 产品定位再确认

| 维度 | 解读结论 |
|---|---|
| 产品本质 | **智能交易辅助决策平台**，定位是"AI 出策略、人做决策"，绝非全自动交易系统 |
| 核心价值链 | 市场数据 → AI 模型 → 交易决策 → 结算复盘 的一体化工作台 |
| 差异化优势 | 预测-决策一体化、多智能体协同、多市场联合优化、人机协同（对标国内厂商"预测与决策割裂、多市场联合优化能力弱、人机协同体验不足"三大短板） |
| 目标客户 | 发电企业 / 售电公司 / 电网企业交易业务部门 |
| 监管合规底色 | 等保三级、信息披露、市场力监测、全链路留痕——合规能力是**准入门槛**而非加分项 |

### 1.2 需求全景与优先级管理

- **P0 需求 18 项**（本期上线必备）：覆盖政策与数据（3项）、智能交易辅助决策（4项）、复盘与结算（2项）、数据管理（5项）、平台与集成（4项）。
- **P1 需求 9 项**（上线后 1-3 月补齐）：短期合同转让、省间现货、售电及长周期中长期决策、系统调优、移动端小程序。
- **P2 需求**：PRD 未列出具体条目，需在需求调研阶段补充远期规划，避免范围蔓延。

**关键结论**：P0 中 **FR-TR-05 多智能体协同决策** 与 **FR-TR-06 多市场联合优化** 是 AI 核心难点，必须最早启动算法预研；FR-INT-01 营销平台对接依赖外部接口，必须最早开展接口调研。

### 1.3 业务闭环解读（G4）

PRD 核心业务闭环：**预测 → 决策 → 交易 → 复盘 → 结算**。

```
①预测（发电/电价/负荷大模型）
   ↓
②决策（多智能体协同 → 多市场联合优化 → 多方案生成）
   ↓
③交易（人机协同确认 → 申报执行 → 成交归集）
   ↓
④复盘（偏差归因 → 策略库更新 → 反哺决策引擎）
   ↓
⑤结算（结算单识别 → 自动核对 → 差异工单 → 成效分析）
   ↑___________________数据回流___________________|
```

**产品基线决策**：
1. 首期以"日滚动中长期 + 省内现货"为主战场（P0 覆盖），省间现货、短期转让作为 P1 扩展；
2. 移动端小程序 P1 阶段建设，但**预警消息通道**需在 P0 平台期预留接口（避免后期返工）；
3. 预测模型是全部决策功能的地基，**模型效果（MAPE 指标）决定产品价值上限**，须作为最高优先级资源保障。

### 1.4 用户价值主张（按角色）

|---|---|---|
| 交易员 | 从"凭经验"到"有依据"：快速获得可执行策略与报价建议 | 决策时长缩短 ≥ 50%，操作路径 ≤ 5 步 |
| 市场分析师 | 政策变化秒级解读，行情趋势多维度透视 | 政策解析准确率 ≥ 85%，研判简报一键生成 |

### 1.5 产品评审意见（PM）

1. **明确本期上线边界**：建议将 P0 全部 18 项作为合同验收范围，P1 作为二期或"上线后 1-3 月"里程碑，在合同中写清边界，防止范围蔓延；
2. **模型指标为验收核心**：MAPE/准确率指标必须写入验收条款，且需要明确"测试数据集来源"（历史真实数据）、"回测周期"（30 天滚动）与"基准线"（对比基线方案），避免验收争议；
3. **人机协同是合规底线**：所有 AI 建议必须"可解释、可驳回、可留痕"，关键决策必须人工确认；
4. **建议补充用户故事（User Story）**：PRD 以功能需求为主，开发基线需补充典型用户故事与验收场景，供测试用例编制；
5. **数据基础依赖预警**：系统效果强依赖营销平台数据质量与气象数据，需在项目启动阶段即开展数据源可用性调研。

### 2.1 架构解读（对 PRD 第五章的深化）

PRD 给出五层架构（业务/应用/技术/数据/集成）。架构师基线决策如下：

### 2.3 关键架构决策记录（ADR）

| ADR 编号 | 决策点 | 决策 | 备选方案 | 理由 |
|---|---|---|---|---|
| ADR-01 | 算法服务与业务服务是否分离 | **分离（双栈）** | 全 Java / 全 Python | 算法迭代频繁、依赖 Python 生态；业务稳定性由 Java 保障；通过 REST/gRPC 通信 |
| ADR-02 | 预测/优化任务执行方式 | **异步化：MQ 任务队列 + 任务状态机** | 同步调用 | 预测全场景 ≤10min、优化 ≤5min，均为长任务，必须异步 + 进度可查 |
| ADR-03 | 多智能体框架 | **LangGraph 图编排 + 可插拔智能体** | 自研编排引擎 | 开箱即用、支持状态图、可追溯；智能体以插件化注册 |
| ADR-04 | 规则引擎 | **自研轻量规则引擎（参数化配置 + 版本化）** | Drools 重量级引擎 | 交易规则是"参数 + 逻辑"组合，自研更易适配各省规则差异，支持规则热更新与留痕 |
| ADR-05 | 大模型部署 | **私有化部署（Qwen 系列量化版）** | 云端 API | 数据不出内网，满足等保与《数据安全法》 |
| ADR-06 | 时序数据存储 | **TDengine** | InfluxDB / TimescaleDB | 电力场景高频写入、多年 96 点序列聚合查询，TDengine 性能与国产化适配更优 |
| ADR-07 | 报表引擎 | **自研模板引擎（模板 + 数据模型 + 导出适配器）** | 商业报表工具 | 报表需适配报送格式（表头/口径说明），自研更可控、支持信创 |
| ADR-08 | 求解器 | **HiGHS 开源优先，预留 Gurobi 适配层** | 直接采购 Gurobi | 求解器抽象层（Optimizer Interface）隔离，规模不满足时切换 |

### 2.4 架构评审意见（架构师）

1. **PRD 未明确部署拓扑**：基线建议"1 主中心 + 可选双中心"，关键服务主备切换（RTO ≤ 4h）；
2. **GPU 算力规划**：模型训练需要 GPU（建议 NVIDIA A100/L20 级别或国产昇腾），推理阶段可用 GPU 共享或 CPU 量化推理，需在资源清单中明确；
3. **接口契约先行**：营销平台接口调研必须在蓝图阶段完成，接口文档（Swagger/OpenAPI）作为基线交付物；
4. **信创适配预留**：数据库、中间件、操作系统需在编码阶段即按标准 SQL/标准接口编写，避免后期替换成本；
5. **监控体系**：Prometheus + Grafana + 日志平台（ELK/Loki），业务监控（任务成功率、预测时效）与基础设施监控双轨。

## 四、高级开发工程师视角：开发规划与难点预判

### 4.1 开发总体策略

- **开发顺序**：数据底座（数据管理）→ 预测模型 → 决策算法 → 业务模块（政策/复盘结算）→ 平台集成 → 移动端；

### 6.4 差异化定位结论（产品经理视角 V1.1 补充）

1. **核心差异化宣言**：国内首个“预测大模型 + 多智能体协同 + 多市场联合优化 + 可解释人机协同”四位一体的发电/售电企业交易决策平台；

3. **对标优势组合**：借鉴清能互联的博弈仿真（市场模拟出清）、羚羊的情报整合（60+ 信息源）、GridBeyond 的对手画像（报价行为分析）、Amperon 的预测产品化（置信区间 + 极端事件捕获）；
4. **必须建立的门槛**：可解释决策依据链（国内竞品均缺失）、多市场联合优化的收益量化回测（需公开报告背书）、规则库版本化快速适配（应对各省规则差异）。

### 6.6 体验对标基线（最终用户视角 V1.1 补充）

1. **盯盘效率对标**：参考羚羊“滚撮盯盘效率 +84%”，本系统设定盯盘类操作效率基线——交易员日均盯盘手动操作 ≤ 30 分钟（自动化提醒 + 一键操作）；
2. **情报获取对标**：参考“60+ 情报源”，本系统情报中心首期整合 ≥ 30 类信息源（行情/气象/政策/公告/舆情），预测摘要推送早于交易开市前 1 小时；
3. **决策可信度对标**：参考国际产品“预测附置信区间”，本系统所有 AI 建议强制展示置信度与误差区间，且支持一键查看“依据链”；
4. **移动协同对标**：盯盘提醒、审批、行情速览三场景移动端全覆盖（P1 小程序）；
5. **复盘体验**：复盘报告生成后自动推送关键结论摘要（对标朗新自动化复盘），管理层看板一屏看懂。

### 3.4.2 数据流向（主链路）

```
营销平台/交易中心/气象
  → 采集适配器（定时/实时）→ 质量校验（完整性/准确性/及时性）
  → ODS 入库 → 清洗标准化（口径统一、单位统一、时区统一）
  → DWD 明细 → 特征工程（气象对齐、日历特征、滞后特征）
  → 预测模型推理（日滚动）→ 预测结果入库（版本化）
  → 决策引擎（多智能体 + 联合优化）→ 策略建议（版本化）
  → 人工确认 → 申报文件 → 成交回填 → 持仓更新
  → 结算数据 → 复盘归因 → 策略库/规则库更新（回流闭环）
```

### 3.4.3 数据治理基线

1. **主数据**：电厂/机组、合同、市场、结算周期主数据统一管理；
2. **数据标准**：统一编码（电源类型、市场类型、时段、费用科目）、统一单位（元/MWh、MW、MWh）、统一时区（北京时间）；
3. **质量规则**：完整性 ≥99.5%、范围校验（价格 [0, 限价上限]）、时序连续性（96 点完整）、逻辑校验（负荷 > 0）；
4. **血缘追踪**：采集任务 → 表 → 字段 → 下游任务 → 报表/模型的字段级血缘；
5. **留痕**：采集、加工、预测、决策全流程留痕，关键数据快照对比。

```

  - 预测/决策结果仅供参考（影子模式），不直接用于申报
```

### 3.12.3 上线窗口与保障

- 上线窗口：建议避开交易申报关键时段（每月结算周期第 1-3 天、现货申报窗口）；

- 上线检查：按 11.2 Go/No-Go 清单逐项确认后方可上线。

### 4.2.6 多市场联合优化（FR-TR-06，P0，AI 核心）

**功能分解**：联合优化模型（多市场/多周期/多约束）、滚动优化（未来 N 日）、灵敏度分析、方案对比与仿真、策略回测（策略库沉淀）。

**优化模型（基线）**：

```
目标：Max Σ(中长期收益 + 省内现货收益 + 省间现货收益 − 偏差考核 − 辅助服务成本)
约束：
  - 机组/场站出力约束（含检修、爬坡、启停）
  - 中长期合同分解约束（电量 + 曲线）
  - 省内现货申报段约束（段数、限价、单调性）
  - 省间通道容量约束 + 省内平衡约束
  - 风险约束（CVaR ≤ 阈值，风险偏好可配置）
求解：两阶段（场景抽样随机优化）/ 鲁棒优化（区间不确定）
      MILP 主问题 + 场景子问题迭代（Benders 分解思想，规模大时）
```

**核心数据模型**：

```
joint_optim_task（联合优化任务）: id, task_type(日滚动/N日滚动/月度),
  horizon_days, scenarios(JSON), objective_weights, constraints(JSON),
  status, elapsed_ms, result_id, created_by
joint_optim_result（优化结果）: id, task_id, trade_date, market_plan(JSON: {
  中长期申报, 省内现货报价, 省间报价}), expected_revenue, risk_metrics,
  sensitivity(JSON), version
backtest_run（策略回测）: id, strategy_code, date_range, market_data_version,
  base_plan(分步决策基准), optimized_plan, revenue_delta(收益提升量化),
  metrics(JSON), status, report_url
strategy_library（策略库）: id, strategy_code, strategy_name, params,
  performance(JSON), status(有效/失效/评估中), source(回测/复盘), updated_at
```

**关键接口**：联合优化触发 POST /api/v1/optimize/joint/tasks、方案查询、灵敏度分析 GET /api/v1/optimize/joint/tasks/{id}/sensitivity、回测执行 POST /api/v1/optimize/backtest、策略库管理 CRUD。

**开发要点**：
- 求解器抽象层（HiGHS 优先，Gurobi 可选）保证可替换；

## 4.3 模块 3：复盘与结算模块（FR-RS-01/02）

**关键接口**：复盘报告生成 POST /api/v1/review/reports/generate、偏差归因查询 GET /api/v1/review/reports/{id}/deviations、策略评估查询、知识回流 POST /api/v1/review/feedback。

## 4.6 AI 决策底座专项（跨模块）

### 4.6.1 预测大模型训练方案

| 模型 | 基线方案 | 特征 | 训练节奏 |
|---|---|---|---|
| 火电功率 | LSTM/Transformer 序列模型 + 物理修正 | 气象、历史出力、检修、燃料 | 日增量 + 周全量 |
| 风光功率 | 物理（NWP 功率曲线） + ML 误差修正（XGBoost/LightGBM） | 气象格点、云量、辐照、风速 | 周全量 |
| 电价 | TFT（时序融合 Transformer）+ 集成 | 负荷预测、供需、新能源、历史价格、日历 | 周全量 + 日增量 |
| 负荷 | TFT/GBDT 集成 | 历史负荷、温度、节假日、经济 | 周全量 + 日增量 |

**评估与上线流程**：离线回测（30 天滚动）→ 指标达标 → 影子运行（并行试跑 1 周）→ 正式上线 → 每日监控（MAPE 漂移检测）→ 自动/手动回滚。

### 4.6.2 多智能体与 LLM 私有化

- LLM 部署：Qwen2.5-14B（量化 INT8/INT4）+ vLLM，GPU 2 卡推理；
- 安全：提示词模板化（限制角色与输出 schema）、输出 JSON schema 校验、敏感信息过滤；
- 成本：策略推理走小模型 + 规则，LLM 仅用于政策解析、复盘总结、智能体语言推理等非高频场景。

### 4.6.3 联合优化求解性能预案

- 规模预估：省内现货 96 点 × 申报段数（如 5 段）× 机组数（如 50 台）= 24,000 决策变量级；
- 求解策略：问题分解（中长期 / 现货两阶段迭代）、聚合（机组聚类）、时间窗聚合（高峰低谷分段）；
- 兜底：求解超时 → 返回启发式可行解 + 标记"次优"，确保交易窗口不延误。

## 5.2 通用设计约定（数据库基线）

1. 所有业务表含 `id`（BIGSERIAL/雪花 ID）、`created_at`、`updated_at`、`version`（乐观锁）、`deleted`（软删除）；
2. 金额字段 `NUMERIC(18,4)`（元），电量 `NUMERIC(18,4)`（MWh），价格 `NUMERIC(12,4)`（元/MWh），功率 `NUMERIC(12,4)`（MW）；
3. 时间统一 TIMESTAMP（北京时间，无时区歧义）；日粒度字段 `trade_date`（DATE）；
4. 曲线类数据统一 JSONB（96 点数组或 {point: value}），明细类走时序库；
5. 敏感字段（合同价格、结算金额）加密存储（应用层 AES-GCM）；
6. 大表分区：settlement_record、declaration、audit_log 按月分区；TDengine 按天自动分区。

## 5.3 接口规范基线

### 5.3.1 统一响应结构

```json
{
  "code": 0,              // 0=成功；非 0 为业务错误码（见错误码表）
  "message": "success",
  "data": {},
  "traceId": "uuid",      // 全链路追踪
  "timestamp": 1723104000000
}
```

### 5.3.2 错误码分段规划

| 段 | 含义 | 示例 |
|---|---|---|
| 0xxx | 通用（参数/鉴权/限流） | 1001 未登录、1002 无权限、1003 参数错误、1004 限流 |
| 1xxx | 政策与市场 | 1101 政策解析失败 |
| 2xxx | 预测 | 2101 预测任务不存在、2102 模型未上线 |
| 3xxx | 交易决策 | 3101 合规校验未通过、3102 求解超时 |
| 4xxx | 结算 | 4101 结算单识别低置信、4102 核对差异已存在 |
| 5xxx | 数据管理 | 5101 数据质量校验失败 |
| 6xxx | 平台 | 6101 审批流异常、6102 消息推送失败 |

### 5.3.3 API 命名与分页约定

- RESTful：资源名复数、动词用 HTTP 方法；路径前缀 `/api/v1/{service}`；
- 分页：`page`、`size` 参数，响应 `{list, total, page, size}`；
- 异步任务统一返回 `taskId`，提供 `GET /tasks/{taskId}` 查询进度；
- 所有写操作支持幂等（`Idempotency-Key` 请求头）。

## 6.2 模型评估规范（防"过拟合验收"）

1. **数据划分**：训练集（近 2 年） / 验证集（近 3 个月） / 测试集（最后 30 天），测试集验收前锁定不可见；
2. **滚动回测**：30 天逐日滚动预测，与真实值对比，计算 MAPE、方向准确率等指标；
3. **基准对照**：每个模型必须有对比基准（如持续预测、上周同期、行业通用模型），改进幅度需量化；
4. **季节覆盖**：回测区间须覆盖不同季节/天气场景（至少含 1 个极端天气事件）；
5. **结果可复现**：随机种子固定、代码版本与数据版本记录，MLflow 全量追踪。

## 7.3 CI/CD 流水线

| 阶段 | 工具 | 门禁 |

| 发布 | 镜像版本标签 + 回滚预案 | 发布审批 |

## 7.4 代码评审制度

1. 所有 feature 分支合并 develop 前必须 Code Review（≥1 名高级工程师）；

4. Review 检查清单：安全（OWASP）、并发（幂等/锁）、性能（N+1/索引）、可追溯（审计日志）。

| 预测服务不可用 | 使用上一版本预测结果 + 页面标注"历史预测" + 告警 |
| 营销平台数据未到 | 自动重试（指数退避 3 次）→ 手工补录 → 用历史同期数据兜底 |
| 优化求解超时 | 返回启发式可行方案 + 标记"次优" + 告警 |
| LLM 服务不可用 | 规则引擎 + 模板匹配兜底（政策解析降级为人工标注入口） |
| 报表引擎异常 | 延迟重生成 + 告警，不影响交易核心链路 |

```

```
