## 1. 引言

### 1.1 目的

依据软件工程测试方法，规划 PTIDSS 系统测试的策略、范围、环境、用例组织、进度与质量标准，确保 SRS 42 项功能需求与 NFR-01~33 非功能需求逐项验证，支撑 PRD §14 验收标准（功能验收、性能验收、模型指标验收、集成验收）。

### 1.2 测试层级模型

```
单元测试 → 集成测试 → 系统测试 → UAT 验收测试 → 上线前回归测试
（开发）   （接口/DB）  （功能+非功能）  （业务验收）    （全量回归）
```

### 1.3 测试原则

1. **需求追溯闭环**：每个 FR 至少一个测试组，用例编号关联需求（T-PD-01 等，对齐 SRS §8 追溯矩阵）；
2. **多角色视角**：7 类角色（admin/trader/analyst/settlement/manager/compliance/mobile）分别验证权限矩阵与功能可用性；
3. **真实环境优先**：后端 9080 + PostgreSQL + TDengine 真实实例，禁用 mock 替代业务验证；
4. **验证码可控**：测试执行用 `--ptidss.captcha.enabled=false` 绕过图形验证码，生产态单独验证验证码链路；
5. **数据隔离**：测试数据与种子数据分离，用后清理（DELETE 残留归零校验）。

## 2. 测试策略

### 2.1 单元测试（开发阶段）

| 项 | 说明 |
|---|---|
| 范围 | Service 层核心逻辑（状态机、权限切面、加密、区域路由） |
| 工具 | JUnit + Mockito（后端）；Vitest（前端组件） |
| 覆盖率目标 | 核心 Service 语句覆盖率 ≥70%（PRD §12.3） |
| 重点 | PreAuthorizeAspect 权限矩阵、ServiceException 业务码、MybatisMetaObjectHandler 雪花 ID |

### 2.2 集成测试（接口层）

| 项 | 说明 |
|---|---|
| 范围 | 22 个 Controller / 90 个端点契约验证 |
| 工具 | Python requests 脚本（tests/full/）、psql 落库校验 |
| 重点 | 入参枚举校验、分页契约、X-Region-Code 区域路由、认证/授权 14001/14003、数据落库 |
| 既有资产 | 全量模拟测试 113 用例、补充测试 9 用例、新增 API 16 用例（tests/full/） |

### 2.3 系统测试（功能）

按 SRS 3.1~3.9 模块分组执行用例（见 §4 矩阵），含端到端主流程（预测→决策→申报→复盘→结算）。

### 2.4 非功能测试

| 类型 | 指标 | 方法 |
|---|---|---|
| 性能 | NFR-01 接口 P95 ≤3s；NFR-06 并发 ≥100 | 压测脚本（tests/performance/），P95 统计 |
| 前端 | NFR-02 页面加载 ≤3s；NFR-07 图表渲染 ≤2s | 浏览器实测 + Lighthouse |
| 安全 | NFR-14~19 | 越权用例（非 admin 调写 API 应 14003）、验证码链路、敏感字段加密抽查 |
| 审计 | NFR-15/31 | 关键操作后 audit_log 落库校验 |

### 2.5 UAT 与回归

- UAT：7 角色业务代表按原型/PRD 验收要点逐项确认；
- 回归：每次版本变更后全量回归（113+9+16 用例基线），缺陷关闭率 100%、严重缺陷归零（PRD §14.5）。

## 5. 关键测试用例设计（代表）

### 5.1 登录与认证链路

```
CASE-AUTH-01：验证码开启时无验证码登录 → 返回 code=500 "请输入验证码"
CASE-AUTH-02：错误密码 → 认证失败提示
CASE-AUTH-03：正确凭据（Ptidss@2026 + X-Region-Code）→ data.accessToken 非空
CASE-AUTH-04：GET /auth/current 恢复用户态（roles/permissions/regions）
CASE-AUTH-05：无令牌访问业务端点 → 14001
```

### 5.2 权限门禁（写操作 admin 收紧）

```
CASE-PERM-01：trader01 POST /data/sources → 14003（缺少角色 admin）
CASE-PERM-02：trader01 POST /intel/sources → 14003
CASE-PERM-03：trader01 POST /policy/upload → 14003
CASE-PERM-04：trader01 POST /data/collect-tasks → 14003
CASE-PERM-05：trader01 POST /intel/push-rules → 14003
CASE-PERM-06：admin01 同端点 → code=0
```

### 5.3 业务规则用例

```
CASE-RULE-01：数据源重复编码 → 业务错误（5xxx）
CASE-RULE-02：非法枚举（sourceType=xxx）→ 业务错误
CASE-RULE-03：决策会话创建 → 状态 orchestrating → 轮询至 generated
CASE-RULE-04：会话确认 → humanReviewStatus=confirmed
CASE-RULE-05：申报单创建 → complianceCheck 落库 → submit → submitted 禁改
CASE-RULE-06：结算核对 → reconcile 状态 consistent/diff
CASE-RULE-07：OCR 低置信 → reviewStatus=pending → 人工复核后 reviewed
CASE-RULE-08：情报推送执行 → message_record 生成（biz_ref 幂等）
CASE-RULE-09：区域隔离 → CN-32 用户查不到 CN-33 数据
```

### 5.4 端到端主流程用例（PRD §11）

```
CASE-E2E-01（日滚动决策）：预测任务 → 决策会话 → 方案确认 → 申报创建 → 提交 → 成交 → 持仓更新
CASE-E2E-02（结算闭环）：记录同步 → 核对 → 差异工单 → 处理 → 台账
CASE-E2E-03（政策解析）：上传 → 解析 → 条款确认 → 规则沉淀
CASE-E2E-04（情报推送）：新增源 → 情报入库 → 规则匹配 → 消息中心可见
CASE-E2E-05（复盘闭环）：复盘报告 → 偏差归因 → 策略回流 → 策略库更新
```

## 8. 准入准出标准

### 8.1 准入标准（进入系统测试）

- 需求-设计-接口-数据五层文档齐备且通过评审；
- 冒烟测试通过（登录/主流程可用）；
- 严重缺陷（S1/S2）清零。

### 8.2 准出标准（上线放行）

- 全部 P0 用例通过率 100%；P1 通过率 ≥95%；
- 缺陷关闭率 100%，严重缺陷归零（PRD §14.5）；
- 非功能指标全部达标（NFR-01~09）；
- 权限矩阵验证无越权项；审计链路验证完整；
- 回归基线（113+9+16）全绿。

### 8.3 缺陷分级

| 级别 | 定义 | 处置 |
|---|---|---|
| S1 致命 | 系统不可用/数据损坏/安全漏洞 | 立即修复，阻塞发布 |
| S2 严重 | 主流程不可用/关键功能错误 | 本迭代修复 |
| S3 一般 | 次要功能缺陷/边界异常 | 计划修复 |
| S4 建议 | 体验优化/文案 | 评估后处理 |

## 9. 缺陷管理流程

```
发现（测试脚本/人工）→ 记录（用例号+复现步骤+期望/实际）→ 定位（日志 traceId）
→ 修复 → 复测（同用例）→ 回归（全量基线）→ 关闭
```

- 缺陷单要素：编号/模块/需求号/级别/复现步骤/期望结果/实际结果/日志/修复版本；
- 全程留痕：修复前后快照入审计（若为关键操作）。
