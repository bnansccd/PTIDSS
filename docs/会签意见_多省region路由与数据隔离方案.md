## 二、RLS 行级安全最优决策（遗留项 3 定案）

### 评估背景

- 评审决议⑤为 **P0 目标**，种子数据已 3 省 enabled（江苏/上海/浙江），方案 V1.0 建议"≥5 省在线才启用 RLS"——门槛与 P0 现实（3 省即刻在线）存在张力；
- 微服务 8+ 服务共享 PG 连接池，RLS 需每服务独立账号，运维复杂度高；当前为内部系统，无外部多租户/审计强制诉求；
- 应用层过滤的最大风险是**人为遗漏**（铁律 2 靠纪律不可靠）。

### 最优选：首期不启用 RLS + 三重补偿控制

| 决策项 | 结论 | 理由 |
|---|---|---|
| 首期 RLS | **不启用** | 无外部审计强制诉求；RLS 引入连接账号体系重构与每查询策略开销；P0 时间窗内不划算 |
| 补偿 ① | **MyBatis 拦截器统一追加 region 条件** | 机制保障替代纪律：13 张核心表 Mapper 全量拦截，缺 region 即拒绝执行 |
| 补偿 ② | **CI 测试门禁**：断言核心表 SQL 必含 region_code | 静态扫描 + 集成测试双重兜底，防拦截器漏配/绕过 |
| 补偿 ③ | **网关 403 越权拦截**（校验规则 3/4） | 请求级防越权，与应用层过滤互不替代 |
| 触发启用条件 | 全国推广期 **≥5 省在线且**出现多租户化/外部审计诉求 | 单一条件不触发（避免过度设计）；触发后按 5.1 模板启用，每服务独立账号 |

**否决的备选**：
1. 首期即启用 RLS——连接池账号体系重构成本高、查询开销无必要、运维排障复杂（否决）；
2. 完全依赖应用层手写条件——无机制保障，遗漏即跨省数据泄露（否决，以补偿①替代）；
3. 按省拆分数据库/实例——资源翻倍、跨省报表与全国聚合无法实现、运维爆炸（否决，与 Doris 全国聚合冲突）。

## 附录 A：RLS 决策复审记录（2026-08-08，V1.1 → V1.2）

### A.1 复审动因

- 多租户/审计独立诉求**自始成立**：多省并行即多租户形态，等保三级审计（NFR 安全）要求审计日志与业务数据**可按省检索、隔离、取证**，非"未来可能发生"的外部诉求；
- 原「≥5 省在线」触发门槛与 P0 现实（首期 3 省 enabled）脱节，且首期不启用将推迟 RLS 策略、账号体系、测试基线的建立，全国推广期集中补课风险高；
- 原否决项「按省拆分数据库/实例」中，TDengine 按省子表分片、Doris 按省分区在成本可控下物理隔离收益明确，经评估可部分采纳。

### A.2 复审结论（替代原二章定案）

| 决策项 | 复审结论 | 理由 |
|---|---|---|
| 首期 RLS | **启用**（替代原「不启用」） | 多租户/审计诉求自始成立；策略按 region_code 统一模板，新增省份零成本生效；PG 内置策略评估开销经压测预算内（方案十章性能基线）；账号体系随 8.2 数据库实施一并建立 |
| 按机构过滤 | **保留并强化**（原补偿①③升级为主防线之一） | MyBatis 拦截器强制追加 region 条件 + CI SQL 门禁 + 网关 403，与 RLS 互为纵深，不再定位为「补偿」 |
| 业务数据按机构分库 | **采纳**（原否决项 3 部分采纳） | TDengine region TAG → 按省子表物理分片（v1.0.1 勘误条目 1/2，**必须执行**）；Doris 聚合表按省分区/分桶；Redis 前缀、报表按省目录逻辑/物理分片；**PG 不拆物理实例**（保留全国聚合与跨省报表链路），拆 schema/实例列为全国推广期演进项 |
| 触发条件 | **即时满足**（原「≥5 省且多租户/审计诉求」删除） | 多租户/审计诉求自始成立，首期 3 省在线即启用；后续按省份规模评估容量扩容而非 RLS 开关 |
